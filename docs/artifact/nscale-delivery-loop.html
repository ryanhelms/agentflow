01Context

Where we are starting from

Today engineers move Jira tickets by hand, PRs link to tickets only when someone remembers, and Confluence drifts from the code. The decisions below came out of the discovery interview and shape everything that follows.

HostingAll cloudGitHub.com, Jira Cloud, Confluence Cloud. Native connectors and REST APIs are available everywhere; no network bridging.
Jira workflowsVary by teamWe will not force one workflow. Canonical events map to each project's own statuses through a reviewed flow map.
EngineHybridGitHub for Jira app for linking, Jira Automation for Jira-born events, GitHub Actions for everything code-born.
BranchingMixedAutomation keys off events (branch, PR, merge, deploy), not branch names like develop, so trunk-based and GitFlow repos both work.
VersioningSemVer + GitHub ReleasesEvery deployable gets fully automatic releases, versioned per unit and aware of the branching strategy. Production deploys releases only, plus approved hotfixes.
Commit formatConventional + Jira keyfeat(PLAT-123): add quota API #review. Machine-readable for changelogs and for Jira.

Git is the source of truth

Engineers state intent where they already work. Jira and Confluence follow.

Config as code

Status mappings, templates and workflows live in one repo, nscaledev/devflow, changed by PR.

Never block on Jira

If Jira or Confluence is down, commits and merges still go through. Automation retries and reports.

Easy to switch off

Every automation honours a repo variable and a [devflow skip] marker.

02Architecture

Three tools, one loop

The GitHub for Jira app carries development data (commits, branches, PRs, builds, deployments) into Jira's development panel. GitHub Actions make the decisions that depend on our conventions. Jira Automation reacts to things that start in Jira.

System of record writeNotification, config or AI assist

GitHub for Jira app

  • Links commits, branches and PRs to keys it finds
  • Sends build and deployment status to Jira
  • Runs Smart Commit #comment and #time

GitHub Actions (devflow)

  • Enforces the commit and PR convention
  • Moves tickets through the flow map
  • Publishes docs, release notes and reports to Confluence
  • Creates Jira issues from alerts and failures

Jira Automation

  • Epic created → Confluence design page
  • Incident raised → postmortem + Slack
  • Stale-ticket and no-commit nudges

Why the split

  • Transitions need per-team mapping; one YAML file beats one rule copy per project
  • Jira Automation is the better fit when the trigger lives in Jira

03Commit convention

Write it once in the commit

Conventional Commits with the Jira key as the scope. An optional verb at the end of the subject moves the ticket. Commits without a key fail locally and in the PR check.

<type>(<JIRA-KEY>[,<KEY>])[!]: <summary in imperative mood> [#verb]

[optional body: why, not what]

[optional trailers]
Refs: PLAT-456
Devflow: skip
TokenMeaningHandled by
feat fix perf refactor docs test build ci chore revertChange type. Drives changelog sections and semver bumps. ! marks a breaking change.devflow release workflow
#startMove the ticket to the team's "in progress" status.devflow, via flow map
#reviewReady for review. Usually redundant, since opening a PR does the same.devflow, via flow map
#qaHand to QA, for teams with a QA status.devflow, via flow map
#doneClose on merge to the default branch. Ignored on feature branches.devflow, via flow map
#blockFlag as blocked and post the commit body as the reason.devflow, via flow map
#comment <text>Add a Jira comment.Jira Smart Commits
#time 1h 30mLog work.Jira Smart Commits

Repos choose their own merge style. The PR check validates the title and every commit, so the convention holds whether a repo squashes, rebases or merges. On squash-merge repos the PR title becomes the commit on main.

Smart Commits only run when the committer's git email matches a Jira user. Ask engineers to set git config user.email to their @nscale.com address.

05Versioning & releases

Every deployable ships as a versioned release

Apps, services, CLIs, images, Helm charts and libraries all use Semantic Versioning, and every one of them ships as a GitHub Release. The release is the system of record: production deploys reference it, Jira fix versions name it, and Confluence release notes link to it.

Versions come from commits

fix bumps the patch, feat the minor, ! or BREAKING CHANGE: the major. Nobody types a version number.

Fully automatic

Every merge to the default branch with a feat or fix publishes a release within minutes. release-please writes the changelog.

One version per deployable

Each unit in .devflow/releases.yml has its own version. Monorepo tags carry the unit, for example api-v1.4.0.

Production takes releases

A guard blocks production deploys of anything but a published release, except an approved hotfix that must end in a patch release.

Versions follow the branching strategy

Stable versions only come from the default branch. Other branches build prerelease versions that sort before the release they lead to, so every staging image and binary traces back to a release. devflow release init detects the strategy: a develop branch means GitFlow.

BranchTrunk-basedGitFlowExample
mainReleaseRelease1.5.0
developpr prereleasealpha prerelease1.5.0-alpha.7+3f2c1ab
release/*rc prereleaserc prerelease1.5.0-rc.2+9a1b2c3
hotfix/*hotfix prereleasehotfix prerelease1.4.1-hotfix.1+c0ffee1
feature, PRpr prereleasepr prerelease1.5.0-pr.3+abc1234

The number before + counts the unit's commits since its last release, and +sha is build metadata. Before 1.0.0, a breaking change bumps the minor version. Existing tags seed the starting version, so adopting devflow never restarts a version at zero.

07Implementation

Reference implementation

Everything lives in nscaledev/devflow and is tagged v1. Each product repo adds one small caller workflow and a hooks folder. Snippets are starting points to review, not drop-in production code.

Shipped in each repo under .githooks/. Engineers run git config core.hooksPath .githooks once (add it to make setup). The PR check is the real gate; this just catches mistakes early.

.githooks/commit-msg
#!/usr/bin/env bash
# Reject commit subjects that don't follow: type(KEY-123[,KEY-456])[!]: summary
set -euo pipefail
subject=$(head -n1 "$1")

case "$subject" in
  Merge*|Revert*|fixup!*|squash!*|amend!*) exit 0 ;;
esac

types='feat|fix|perf|refactor|docs|test|build|ci|chore|revert'
key='[A-Z][A-Z0-9]+-[0-9]+'
pattern="^($types)\\(($key)(,$key)*\\)!?: .+"

if ! [[ "$subject" =~ $pattern ]]; then
  echo "✖ Commit subject must look like: feat(PLAT-123): add quota API" >&2
  echo "  got: $subject" >&2
  exit 1
fi

Make key-check / validate a required status check through an org ruleset on default and release branches. Start in warn mode (continue-on-error: true) until the P2 exit check passes.

nscaledev/devflow/.github/workflows/jira-key.yml
on:
  workflow_call:

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - name: PR title and every commit carry a real Jira key
        env:
          GH_TOKEN: ${{ github.token }}
          TITLE: ${{ github.event.pull_request.title }}
          PR: ${{ github.event.pull_request.number }}
          REPO: ${{ github.repository }}
          JIRA_BASE: ${{ vars.JIRA_BASE }}
          JIRA_USER: ${{ secrets.JIRA_USER }}
          JIRA_TOKEN: ${{ secrets.JIRA_TOKEN }}
        run: |
          key='[A-Z][A-Z0-9]+-[0-9]+'

          echo "$TITLE" | grep -Eq "$key" \
            || { echo "::error::PR title needs a Jira key, e.g. 'feat(PLAT-123): …'"; exit 1; }

          missing=$(gh api "repos/$REPO/pulls/$PR/commits" --paginate \
                      --jq '.[].commit.message | split("\n")[0]' \
                    | grep -Ev '^(Merge|Revert|fixup!|squash!)' \
                    | grep -Ev "$key" || true)
          if [ -n "$missing" ]; then
            echo "::error::Commits without a Jira key:"; echo "$missing"; exit 1
          fi

          for k in $(echo "$TITLE" | grep -Eo "$key" | sort -u); do
            code=$(curl -s -o /dev/null -w '%{http_code}' -u "$JIRA_USER:$JIRA_TOKEN" \
                   "$JIRA_BASE/rest/api/3/issue/$k?fields=status")
            [ "$code" = 200 ] || { echo "::error::$k not found in Jira (HTTP $code)"; exit 1; }
          done

Called by transitions.yml once per key and event. It finds a transition whose destination is the mapped status, skips if none is reachable, and never moves a ticket backwards (Done-category tickets are left alone).

nscaledev/devflow/bin/transition.sh <KEY> <event|#verb>
#!/usr/bin/env bash
set -euo pipefail
key="$1"; event="$2"; project="${key%%-*}"
map="${FLOW_MAP:-flow-map.yml}"

# event is "pr.merged" etc., or "#qa" for a commit verb.
# Project override, falling back to defaults. An explicit null means "do nothing".
if [[ "$event" == \#* ]]; then path=".verbs[\"${event#\#}\"]"; else path="[\"$event\"]"; fi
target=$(yq -r ".projects.$project$path // .defaults$path // \"\"" "$map")
[ -z "$target" ] || [ "$target" = null ] && { echo "$key: no mapping for $event"; exit 0; }

auth=(-sf -u "$JIRA_USER:$JIRA_TOKEN" -H 'Content-Type: application/json')
issue=$(curl "${auth[@]}" "$JIRA_BASE/rest/api/3/issue/$key?fields=status")
current=$(jq -r '.fields.status.name' <<<"$issue")
category=$(jq -r '.fields.status.statusCategory.key' <<<"$issue")

[ "$current" = "$target" ] && exit 0
[ "$category" = done ] && { echo "$key already done, not moving"; exit 0; }

tid=$(curl "${auth[@]}" "$JIRA_BASE/rest/api/3/issue/$key/transitions" \
      | jq -r --arg t "$target" '.transitions[] | select(.to.name == $t) | .id' | head -n1)
[ -z "$tid" ] && { echo "::warning::$key: no transition from '$current' to '$target'"; exit 0; }

curl "${auth[@]}" -X POST "$JIRA_BASE/rest/api/3/issue/$key/transitions" \
  -d "{\"transition\":{\"id\":\"$tid\"}}"
echo "$key: $current → $target ($event)"

Shared by docs sync, release notes and sprint reports. Pages are found by title under a parent and updated in place with the next version number. Pandoc output is close to Confluence storage format; macros such as code blocks get a small post-processing pass.

nscaledev/devflow/bin/confluence-upsert.sh <space-id> <parent-id> <title> <file.md>
#!/usr/bin/env bash
set -euo pipefail
space="$1"; parent="$2"; title="$3"; src="$4"
api="$CONFLUENCE_BASE/wiki/api/v2"
auth=(-sf -u "$JIRA_USER:$JIRA_TOKEN" -H 'Content-Type: application/json')

banner='<p><em>Generated from '"$GITHUB_REPOSITORY"'. Edit in the repo, not here.</em></p>'
html="$banner$(pandoc -f gfm -t html "$src")"

existing=$(curl "${auth[@]}" -G "$api/pages" --data-urlencode "title=$title" \
           --data-urlencode "space-id=$space" | jq -r '.results[0] // empty')

if [ -z "$existing" ]; then
  jq -n --arg s "$space" --arg p "$parent" --arg t "$title" --arg b "$html" \
    '{spaceId:$s, parentId:$p, status:"current", title:$t,
      body:{representation:"storage", value:$b}}' \
  | curl "${auth[@]}" -X POST "$api/pages" -d @-
else
  id=$(jq -r '.id' <<<"$existing")
  ver=$(curl "${auth[@]}" "$api/pages/$id" | jq '.version.number + 1')
  jq -n --arg id "$id" --arg t "$title" --arg b "$html" --argjson v "$ver" \
    '{id:$id, status:"current", title:$t, version:{number:$v, message:"devflow sync"},
      body:{representation:"storage", value:$b}}' \
  | curl "${auth[@]}" -X PUT "$api/pages/$id" -d @-
fi

Built in the Jira Automation UI as global rules scoped to opted-in projects, owned by the Engineering Enablement service account. Keep the exported JSON in nscaledev/devflow/jira-automation/ so changes are reviewed.

RULE  Epic → design doc
  When   Issue created
  If     Issue type = Epic
  Then   Create page (Confluence) in the team space, template "Design Doc"
         title: "{{issue.key}} · {{issue.summary}}"
  And    Comment on issue with the page link

RULE  Incident → postmortem + Slack
  When   Issue created
  If     Issue type = Incident AND priority in (P1, P2)
  Then   Send Slack message to #incidents (webhook)
  And    Create page from "Postmortem" template, link on the incident
  When   Issue transitioned to Resolved
  Then   Create sub-task "Postmortem review", due {{now.plusBusinessDays(5)}}

RULE  In Progress with no code (weekdays 09:00)
  When   Scheduled, JQL:
         statusCategory = "In Progress" AND updated <= -5d
         AND development[commits].all = 0
  Then   Comment mentioning the assignee and send a Slack digest to the team channel

RULE  Blocked → Slack
  When   Issue transitioned to Blocked
  Then   Send Slack message to the team channel with the last comment

08Developer plugin

devflow in every AI terminal

The Actions above react after code is pushed. devflow works earlier, inside the developer's AI client, so the agent knows the ticket, writes the commit correctly the first time, and shows what will happen in Jira before anything changes. It works the same in Claude Code, Codex CLI, Grok CLI, Cursor, Copilot, Gemini CLI and a plain terminal.

One binary, three faces

A single Go binary is the CLI, the MCP server (devflow mcp) and the git hooks. Every client gets the same behaviour.

The client's model writes

devflow never calls an LLM. It gives the agent context and rules, then validates what the agent writes. No extra API keys, any model.

Hooks enforce, clients assist

Rules that must hold are enforced by git hooks and CI. Client hooks such as Claude Code's only make the experience smoother.

Your identity, your autonomy

Writes use the developer's own Atlassian and GitHub tokens. Each developer chooses suggest, confirm or auto, within limits the repo sets.

Releases and auto-update

devflow releases from a single branch. No one picks version numbers, and there is no Release PR. Every merge to main is checked against the commit types since the last vX.Y.Z tag: fix bumps the patch, feat the minor and ! the major. If there is a bump, the release workflow generates that version's CHANGELOG.md section from the commits, commits it as chore(release): vX.Y.Z, tags it and publishes a signed GitHub Release with the same notes within minutes. Running installs pick it up on their next check. The repo enforces the same commit convention as the repos devflow manages, locally and in CI, and CHANGELOG.md is never edited by hand.

How a running install updates

MomentWhat devflow does
Every start (CLI, hook, MCP)If the last check was more than 6 hours ago, start a background check. It never delays the command or the MCP handshake. Offline or rate-limited means keep running the current version and retry later.
New version foundDownload into a staging folder, verify the SHA-256 from checksums.txt and the GitHub build attestation, extract into ~/.cache/devflow/<version>/, then swap the current symlink atomically. A half-finished download never becomes current.
Long MCP sessionsThe MCP server re-checks every 6 hours while running. A running server never replaces itself mid-session. Told about itThe CLI prints one line to stderr. Claude Code's SessionStart hook adds "devflow updated to 0.6.0" with the changelog link. MCP clients get the log notice.
CleanupKeep the current and previous versions for rollback, and delete older ones.
Forced updateOn start, devflow reads policy/versions.json from nscaledev/devflow. If its own version is below min_version or on the blocked list, it updates before doing anything else. If it can't update, it stops with a clear message instead of running a bad build.

#!/bin/sh
# Project launcher: run the installed devflow, or bootstrap the latest release.
set -eu
home="${XDG_CACHE_HOME:-$HOME/.cache}/devflow"
[ -x "$home/current/devflow" ] && exec "$home/current/devflow" "$@"

os=$(uname -s | tr '[:upper:]' '[:lower:]')
case "$(uname -m)" in x86_64|amd64) arch=amd64 ;; arm64|aarch64) arch=arm64 ;; esac
tag=$(gh release view --repo nscaledev/devflow --json tagName -q .tagName)   # latest stable
ver=${tag#v}; pkg="devflow_${ver}_${os}_${arch}.tar.gz"
tmp=$(mktemp -d); trap 'rm -rf "$tmp"' EXIT

echo "devflow: first run, installing $tag" >&2
gh release download "$tag" --repo nscaledev/devflow --dir "$tmp" \
   --pattern "$pkg" --pattern checksums.txt >&2
(cd "$tmp" && grep " $pkg\$" checksums.txt | shasum -a 256 -c -) >&2
gh attestation verify "$tmp/$pkg" --repo nscaledev/devflow >&2

mkdir -p "$home/$ver" && tar -xzf "$tmp/$pkg" -C "$home/$ver" devflow
ln -sfn "$home/$ver" "$home/current"
exec "$home/current/devflow" "$@"

The workflow commits the generated CHANGELOG.md section, tags that commit and GoReleaser publishes the release with the same notes. It needs no GitHub App. If the build fails, the tag is removed so the next merge retries.

          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"

            --repo "$GITHUB_REPOSITORY" --notes "$RUNNER_TEMP/release-notes.md" --update CHANGELOG.md
          git add CHANGELOG.md
          git commit -m "chore(release): v$VERSION"
          git tag -a "v$VERSION" -m "devflow v$VERSION"

      - name: Build and publish the GitHub Release
        if: steps.version.outputs.release == 'true'
        uses: goreleaser/goreleaser-action@v6

          GITHUB_TOKEN: ${{ github.token }}

The core of internal/update. Every entry point calls Enforce first and then Background. Verification uses the same two checks as the launcher, through the GitHub attestation API and Sigstore libraries.

internal/update/update.go (excerpt)
// Enforce runs before anything else. It only blocks if this build must not run.
func (u *Updater) Enforce(ctx context.Context) error {
	pol, err := u.policy(ctx) // policy/versions.json, ETag-cached; nil when offline
	if err != nil || pol == nil || !pol.Requires(Version) {
		return nil
	}
	rel, err := u.latest(ctx)
	if err == nil {
		err = u.install(ctx, rel)
	}
	if err != nil {
		return fmt.Errorf("devflow %s is blocked (%s) and the update failed: %w", Version, pol.Message, err)
	}
	return ErrRestartRequired // CLI re-execs into the new binary; MCP returns this on every tool call
}

// Background never blocks the caller. Safe to call from CLI, hooks and the MCP server.
func (u *Updater) Background(ctx context.Context) {
	if u.disabled() || u.cfg.Pin != "" || !u.due() {
		return
	}
	go func() {
		defer u.touch()                       // record the check time even on failure
		rel, err := u.latest(ctx)             // channel + track aware
		if err != nil || !rel.NewerThan(Version) {
			return
		}
		if err := u.install(ctx, rel); err != nil {
			u.log.Warn("update failed, staying on current", "version", rel.Version, "err", err)
			return
		}
		u.notify(rel) // stderr line, MCP log notice, SessionStart message
	}()
}

// install: download to staging, verify checksum and attestation, extract, swap symlink.
func (u *Updater) install(ctx context.Context, rel Release) error {
	unlock, err := u.lock() // file lock: two sessions never install at once
	if err != nil {
		return err
	}
	defer unlock()
	dir, err := u.stage(ctx, rel)
	if err != nil {
		return err
	}
	if err := u.verify(ctx, dir, rel); err != nil {
		return err
	}
	if err := u.activate(dir, rel.Version); err != nil { // rename + atomic symlink swap
		return err
	}
	return u.prune(2) // keep current + previous
}

Plugin guardrails

Identity and secrets

  • Writes use each developer's own Atlassian API token and gh token, so Jira and GitHub history shows the real person
  • Tokens live in macOS Keychain, Secret Service or Windows Credential Manager, never in files or MCP responses
  • An Atlassian OAuth app (planned) would replace personal API tokens and let one revocation cut off every install

Untrusted content

  • Ticket, comment and Confluence text is returned in labelled reference blocks, and agents are told not to follow it
  • Remote writes whose payload came from ticket text still need confirmation, whatever the autonomy level
  • The diff is scanned for secrets before every commit and PR

Safety and audit

  • Built-in "never" list: force-push, protected-branch push, merges, remote branch deletes
  • Every local and remote action is written to ~/.devflow/audit.log with client, tool and payload hash
  • Atlassian rate limits respected with backoff; reads cached for 60 seconds per session
  • Updates only install when both the checksum and the GitHub build attestation from nscaledev/devflow verify

The provider migration rehearsal records caller pins, compares previews, verifies replay, and restores baseline settings before consumer rollout.

09Rollout

Gate No phase starts until Kyle Redelinghuys and Vishal Srini approve this architecture and plan. The nscaledev/devflow repo is built and tested so P0 can begin as soon as they sign off.

Phases are gated by outcomes, not dates. A phase starts only when the previous one has passed its exit check, and we widen the rollout only when the pilot team says the automation saves more time than it costs.

10Governance

Security, ownership and measuring it

Access

  • One Atlassian service account with a scoped token, limited to opted-in projects and spaces
  • Rotate tokens every 90 days; rotation runbook lives in devflow
  • Workflows request least-privilege permissions: and pin third-party actions to a SHA
  • No secrets ever appear in commit messages, PR bodies or Jira comments

Failure handling

  • Automation never fails a merge because Jira or Confluence is down; it warns and retries
  • Every action leaves a Jira comment or Actions log line saying what changed and why
  • Respect Atlassian rate limits: back off on HTTP 429 and batch JQL lookups

Ownership

  • Engineering Enablement owns nscaledev/devflow and the Jira Automation rules
  • Team leads own their flow-map.yml block
  • Eng managers jointly own the shared Confluence templates
  • Changes ship as tagged releases; repos stay on @v0

Success measures

95%
Commits and PRs linked to a Jira key
−80%
Manual Jira status changes by engineers
<10 min
Release to published release notes
0
Confluence pages older than the code they describe

Targets are proposed. Baselines get measured in Phase 0 from Jira changelog and GitHub API data.
