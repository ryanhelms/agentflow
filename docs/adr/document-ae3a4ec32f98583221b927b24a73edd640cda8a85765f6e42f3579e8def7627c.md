# Provider contracts and repository configuration

## Status

Accepted for the devflow pilot. Consumer rollout follows the compatibility canary and rollback rehearsal.

## Context

Devflow coordinates local Git, task management, knowledge, code hosting, and delivery automation. Existing repositories use Jira, Confluence, and GitHub. Teams need to select services independently while keeping the same CLI, MCP, and workflow operations.

## Decision

Devflow owns typed contracts for the objects it reads and writes. Providers translate those objects to their native APIs or file formats. Devflow resolves code hosting from Git remotes and keeps Task Management, Knowledge Base, DevOps, SecOps, and Notifications in separate configuration sections. DevOps checks, deployments, and releases can use separate providers.

Schemas define defaults and validate overrides for each selected provider. Devflow resolves a task template before creation and retains its revision for later operations when the provider supports that metadata. Qualified references preserve identity across branches, commits, pull requests, and provider instances.

FileSystem stores tasks and documents as Markdown with front matter. Repository adds Git publication, revision checks, and support for review through a pull request. Each runtime plans its provider tooling independently. CLI and MCP use the same setup and operation policies.

## Consequences

Existing Jira and Confluence selections retain their compatibility path. GitHub Issues and Repository knowledge serve the devflow pilot. The delivery plan separates the product's GoReleaser workflow from the release-please workflow used by consumer repositories.

The pilot checks repository-scoped references, repeatable setup, approval boundaries, and one issue transition after an authorized merge. Consumer rollout also needs recorded replay and rollback results.
